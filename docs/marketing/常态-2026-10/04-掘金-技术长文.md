# 我用 Flutter 做了一款拍照姿势剪影引导 App：从取景框叠加剪影到鸿蒙上架

> 本文来自「如画 Lumira」开发记录。这是一款把摆姿经验做成"取景框内叠加姿势剪影"的摄影辅助 App，同一套 Dart 代码库同时支持鸿蒙 HarmonyOS 与 iOS。本文只讲工程里已经落地的东西，涉及实现的部分都能在代码里找到对应。

## 一、要解决的问题

拍照出不了片，很多时候不是相机不行，而是"不知道往哪站、手往哪放"。构图和姿势这件事，专业摄影师靠经验，普通人靠猜。我们的思路很直白：**把一张姿势参考图，直接叠在取景框上**——用户看到的是"成片画面里人应该占的位置和形态"，而不是一段抽象的构图口诀。

听起来只是"盖一张图"，真正做起来要回答三个问题：剪影怎么定位才和成片对得上？它怎么不干扰相机本身的手势？换成像比例、换姿势之后怎么不跑位？下面按这三条讲。

## 二、剪影叠加：一张图背后的坐标系

取景器本质是一个 `Stack`。相机预览在底层，往上依次是构图辅助线、姿势剪影、对焦反馈层。剪影这一层的核心代码在 `features/templates/widgets/pose_silhouette.dart`，外层是 `SilhouetteLayer`，在取景器里这样挂载（`camera_preview.dart`）：

```dart
final silhouetteOverlay = (hasSilhouette && showSilhouette)
    ? Positioned.fill(
        child: IgnorePointer(          // 关键：不吃手势，对焦/捏合缩放在下层照常工作
          child: SilhouetteLayer(
            silhouetteType: silhouetteType,
            silhouetteData: silhouetteData,
            positionX: silhouettePosX,  // 0..1，相对成像区宽
            positionY: silhouettePosY,  // 0..1，相对成像区高
            scale: silhouetteScale,
            rotation: silhouetteRotation,
          ),
        ),
      )
    : const SizedBox.shrink();
```

定位规则定在**成像区**这套坐标系里，而不是屏幕：

- 剪影框宽 = 成像区宽 × 40%，宽高比固定 1:1.6（人像纵向）；
- 剪影中心锚定在 `(成像区宽 × positionX, 成像区高 × positionY)`，用 `FractionalTranslation(-0.5, -0.5)` 把锚点从左上角挪到中心；
- `scale` / `rotation` 在基础尺寸上叠加。

好处很实在：positionX/positionY 存的是 0~1 的百分比。用户从 4:3 切到全屏，成像框尺寸变了，剪影按新的框重新算，位置自然跟着走，不会出现"换比例后剪影飘到屏幕角落"。这是我们在模板数据里存百分比而非固定像素的原因。

**渲染方式按资源类型分流**，这也是一个取舍点：

- `builtin`：内置剪影是**黑色线条 PNG（透明背景）**，直接 `Image.asset`。因为叠在照片/取景画面上需要浅色，这里用了一个 `ColorFilter.matrix` 做反色（黑→白），不额外维护一套白色素材；
- `image`：交给统一的图片组件按来源分流（asset / http / 本地文件 / base64）；
- `svg`：只支持我们自己的编辑器导出的极简格式，用 `CustomPaint` 逐条 `path` 描边绘制。**没有引入通用 SVG 解析库**——为一个受限的导出格式背上整个解析器不划算，正则取 `<path>` 的 `d`、只认 `M`/`L` 指令，够用且可控。

另外，多姿势模板里剪影跟随当前选中的姿势：`currentPoseIndexProvider` 一变，读取的 `silhouette.type/data/scale/rotation/position` 整体切换，横向滑动即可换姿势。剪影层与相机预览是**两个独立的层**，所以切姿势不会重建相机会话。

## 三、工程结构：分层与离线优先

代码按 `core / shared / features` 分层：

- `core/`：数据库、主题、网络、路由、配置等横切能力；
- `shared/`：跨 feature 复用的组件与工具（按钮、卡片、导航、海报等）；
- `features/`：按业务域切分（capture 拍摄、templates 模板、gallery 相册、inspiration 灵感……），每个 feature 内部再分 `pages / widgets / services / data`。

状态管理用 `flutter_riverpod`，数据库、鉴权、主题都通过 provider 暴露。这里遇到的一个硬约束是版本：鸿蒙侧锁定 **Flutter 3.7.12 / Dart 2.19.6**，所以 `flutter_riverpod` 被钉在 **2.3.6**（更高版本会连带把 `meta` 拉到 Dart 3 才有的版本），`go_router` 用 6.5.7。这类"降级链"在鸿蒙 fork 上很常见，做法是先建一张依赖兼容表，从锁文件反向约束，而不是让解析器自由发挥。

**离线优先**落在一个 sqflite 本地库（`lumira.db`，schema 版本 60）上：内置模板、分类、场景在首装时由种子器写入本地；照片、打卡、收藏、水印、通知、搜索历史各自有 DAO；远端数据通过一层 API 缓存 DAO 落库，断网时优先读本地。启动时只打开一次数据库，`onCreate` 负责建表 + 种子化，`onUpgrade` 负责逐版本的迁移。抽象上，数据库本身是一个 `FutureProvider`，业务 DAO 通过它惰性解析连接——**UI 不直接碰 sqflite**。

## 四、四套 UI 风格与 8 套主题怎么抽象

设置里有 4 种 UI 风格（新拟态 / 扁平 / 玻璃 / 女性美学）和 8 套主题色。我们没有为每套风格写一套页面，而是把它们抽成两层数据：

- `ThemeKey` 决定色板，产出 `ThemeTokens`（canvas / surface / textPrimary / divider / brand …）；
- `UIStyle` 决定"形态"，由 `AppThemeData` 提供风格相关派生值：`cardRadius`、`surfaceAlpha`、`cardBorder`、`cardShadow`。

页面只消费 `ref.watch(appThemeProvider)`，从不硬编码 `Colors.xxx` 或写死阴影。比如新拟态的卡片阴影是双向浮雕、扁平是无阴影 + 细描边、玻璃是低透明度表面，这些差异都收敛在 `AppThemeData` 的 getter 里。主题与风格都持久化在本地设置表，并在 `runApp` 之前读回，避免首帧闪变。

这里还有一条我们踩过、后来写成规范的边界：**组件落在什么底色上，决定了它能不能用浮雕**。普通卡片在纯色画布上，新拟态的双向阴影成立；但同样一张卡叠在照片上时，照片接不住同色阴影，视觉上会糊成光晕，这时就应退化成"实心表面 + 细描边"、不做模糊和玻璃。判断标准是底色，不是组件类型。

## 五、鸿蒙适配与上架的几点经验

鸿蒙 NEXT 不再兼容 AOSP，所有走 Android 实现的插件在鸿蒙上都是"零实现"。我们按三类处理，这套经验对普通 App 也适用：

1. **有社区鸿蒙适配版 → 换源对齐版本**。数据库、权限、文件选择、设备信息、屏幕常亮等，改用社区维护的适配版本；业务层只 import 自己的接口层，由包装器按平台运行时分发（如文件选择，iOS/Android 走原版、鸿蒙走 ohos 包，API 一致）。
2. **没有适配版 → FFI 未必可行**。我们试过用 FFI 绕开原生插件直接加载 so，后来因 so 重定位不兼容而放弃，回到适配版。评估顺序应是：先查适配库清单，再考虑自研。
3. **有适配版但有 bug → 自建 fork**。相机插件我们本地化维护并打了预览一致性补丁——拍照 App 里"取景器所见 = 成片"是产品成立的前提。

几个具体的适配点：传感器能力（水平仪）在 iOS/Android 用现成插件、鸿蒙走自建事件通道；扫码在鸿蒙走系统扫码能力的通道；分享不可用时降级到剪贴板并给出提示。另外一个容易被忽略的门槛是**启动时延**——应用市场审核对"启动加载完成时延"有明确指标，我们把数据库打开和种子化从首帧关键路径挪到后台异步，`runApp` 不等它，首帧先渲染出来。

## 六、踩坑与心得

- 叠层一定用 `IgnorePointer` 包住，否则剪影会把手势全吃掉，对焦和捏合缩放全废；
- 坐标存百分比、不存像素，比例切换和不同机型才会一致；
- 端侧差异要认。iOS / 鸿蒙的取景器效果可以下沉到原生 GPU 逐帧管线做到所见即所得，Android 端我们则只保证色彩矩阵实时、细节效果作用于成片，这是能力差异下的务实选择；
- 版本锁死是鸿蒙适配的常态，先建兼容表、关键 fork 本地化，能省掉大量"编译通过、运行时才炸"的排查。

## 七、结语

把所有东西塞进取景框这件事，技术难度不在某一处，而在"预览、叠加、成片、存储、多平台"这一整条链路都要对齐。目前「如画 Lumira」在**鸿蒙应用市场已上架**，**iOS 版正在审核、即将上架**。应用商店搜索「如画 Lumira」即可找到。

# 【第二波 · 2026-10-05】取景器上叠一层"人形剪影"难在哪？Flutter 相机叠加层的坐标系与手势实战

> 第二波定位：**更吸睛 · 更聚焦**。上一篇是产品与工程的纵览，这一篇只钻一个点——"剪影叠加层"背后的**坐标系设计**与**手势透传**。所有实现细节均来自仓库中真实代码（`pose_silhouette.dart` / `camera_preview.dart`）。

## 一、把一张图"盖"在取景器上，为什么不是一行 Image

需求听起来朴素：选一个模板，把一张人形剪影参考图叠在相机预览上，用户照着站。

第一版实现很快就完成了：`Stack` 里相机预览在底，`Image.asset(剪影)` 在上，`Positioned` 给个坐标。上线测试，三个问题立刻冒出来：

1. **手势全废**。剪影层盖上去之后，点屏幕对焦没反应，双指捏合不缩放——手势全被最上层吃掉了。
2. **换比例就飘**。用户从 4:3 切到全屏，剪影跑到画面角落去了。
3. **多姿势切换时相机重启**。滑动换一个姿势，整块相机会话被重建，取景黑一下。

下面按这三条，讲我们最后是怎么定的方案。

## 二、坐标系：为什么位置必须存百分比

先看定位规则。剪影不是"随便摆一个位置"，它有明确的规格（与设计稿对齐）：

- 剪影框宽 = 成像区宽 × **40%**（`PoseSilhouette.baseWidthFactor`）；
- 宽高比固定 **1 : 1.6**（人像纵向，`baseAspectW/baseAspectH`）；
- 剪影中心锚定在 `(成像区宽 × positionX, 成像区高 × positionY)`，`positionX/positionY` 是 **0..1 的百分比**。

关键在最后一条。如果模板数据里存的是"距左上角 320px"这类绝对像素，那么一旦取景区尺寸变化（换机、横竖屏、4:3 ↔ 全屏），剪影位置立刻错位。存百分比后，同一个 `positionX=0.5` 在 4:3 框和全屏框里都表示"水平居中"，位置随比例框自动重算。

落地的两处细节：

```dart
// SilhouetteLayer：把 left/top 指向"中心"，再用 FractionalTranslation 回退半格
Positioned(
  left: areaW * positionX,
  top: areaH * positionY,
  child: FractionalTranslation(
    translation: const Offset(-0.5, -0.5), // 锚点从左上角挪到中心
    child: SizedBox(width: baseW, height: baseH, child: PoseSilhouette(...)),
  ),
)
```

`FractionalTranslation(-0.5, -0.5)` 是个不占额外测量的技巧：`Positioned` 给的是剪影框左上角，(0.5, 0.5) 表示百分比居中的语义，用 `FractionalTranslation` 把锚点整体回移半个自身尺寸，就不必额外知道剪影框的实际宽高。配合 `LayoutBuilder`，整个 `SilhouetteLayer` 只需知道自己落在多大的成像区里，其它全按比例算。

`scale` / `rotation` 则是在 40% 基础尺寸之上再叠加的 `Transform`，与位置解耦。

## 三、手势透传：IgnorePointer 与手势竞技场

第一版手势全废，是因为剪影层默认参与了命中测试。修法很直接——把纯展示的叠加层包进 `IgnorePointer`：

```dart
final silhouetteOverlay = (hasSilhouette && showSilhouette)
    ? Positioned.fill(
        child: IgnorePointer(          // 不吃手势，对焦/捏合在下层照常工作
          child: SilhouetteLayer(...),
        ),
      )
    : const SizedBox.shrink();
```

`IgnorePointer` 让这一层对命中测试"透明"，事件落到下层的相机预览。同理，构图辅助线（三分法、黄金螺旋）也是纯展示，一并 `IgnorePointer`。

但取景器上不止"透传"这一种需求——捏合缩放、长按锁焦、轻点对焦，是**同一块区域上的多种手势**，会进 Flutter 的手势竞技场（GestureArena）。我们最终的手势分配是：

- **双指捏合** → 缩放；
- **长按**（≥500ms 无位移）→ AE/AF 锁定；
- **轻点** → 对焦。

处理这块时踩到两个坑，都在 `_PinchZoomCamera` 里：

**坑一：刚落下就"炸"到最大倍数。** Flutter 的 `onScaleStart` 会在手势被接受时重新捕获初始跨度。如果按"当前跨度 / 初始跨度"算缩放，双指刚落下时间距极小，初始比例会得到一个巨大的跳变。解法是用 `dragStartBehavior: DragStartBehavior.start`，并用**相邻两帧 scale 的比值**做增量缩放，而不是对初始跨度做绝对比值：

```dart
final ratio = details.scale / _lastScale; // 相邻帧增量，抵消初始跨度
_lastScale = details.scale;
_currentMultiplier *= ratio;
_applyZoom(_currentMultiplier);
```

同时检测指针数：从 <2 变为 ≥2 时，把 `_currentMultiplier` 重新锚定到当前实际倍数（并 `return`），这样"捏 → 松 → 再捏"不会累积出跳变。

**坑二：长按吃掉捏合 / 捏合吃掉长按。** 二者同处竞技场：长按超过 500ms 由 `LongPress` 胜出（tap/scale 被拒），双指捏合由 `Scale` 胜出。只要不手动在 `onLongPressStart` 里做多余的 `recognizer` 干预，二者天然互斥、互不干扰。

还有个体验细节：轻点对焦后，对焦框旁边会带一条竖直的"太阳"曝光条，此时**单指上下拖动**用于临时补偿曝光（模仿 iOS 原相机）。实现上也是在 `onScaleUpdate` 里用 `pointerCount < 2` 分流：单指走曝光拖动，双指走缩放；一旦第二根手指落下，就退出曝光拖动、回到缩放逻辑。

## 四、渲染分流：三类剪影资源，三条路径

模板里的剪影来源不止一种，我们按 `silhouetteType` 分流，而不是硬套一套通用渲染：

- **`builtin`**：内置剪影是**黑色线条 PNG（透明背景）**。叠在照片/取景画面上需要浅色，所以不额外维护一套白色素材，直接用 `ColorFilter.matrix` 做反色（黑 → 白）：

```dart
ColorFilter.matrix(<double>[
  -1,  0,  0, 0, 255,
   0, -1,  0, 0, 255,
   0,  0, -1, 0, 255,
   0,  0,  0, 1,   0,
]);
```

- **`image`**：交给统一的图片组件 `LumiraImage`，由其按来源分流（asset / http / 本地文件 / base64）。纯 base64 会先补上 `data:` 前缀再走 `Image.memory`。
- **`svg`**：只支持我们自己的剪影编辑器导出的**极简格式**。这里做了一个明确的取舍——**不引入通用 SVG 解析库**。一个受限的导出格式，用正则取出 `<path>` 的 `d`、只识别 `M` / `L` 指令，逐段 `moveTo` / `lineTo` 即可，配上 `CustomPaint` 描边绘制。为一个私有格式背上整个解析器不划算。解析失败则降级为占位图标，不崩。

## 五、端侧拿不准时，就分平台做

相机叠加绕不开"取景器所见 = 成片"（WYSIWYG）这个问题。我们在 `camera_preview.dart` 里做了一个**按平台分叉**的务实决定：

- **iOS / OHOS**：锐化、磨皮、暗角、颗粒 + 色彩矩阵，改由**原生 GPU 逐帧渲染**。Flutter 侧通过 `_PostEffectSync` 把参数推给原生管线（`PreviewEffectProcessor` / `libpreview_fx.so`），并做 **16ms 去抖**避免每帧刷原生；参数为全中性时把矩阵传 `null`，让原生处理器保持不激活、走免 GPU 的直通快路径。取景器与成片走同一通道，因此 Dart 层不再叠加 `ColorFiltered`，避免双重矩阵。
- **Android**：只保证色彩矩阵实时（`_PostEffectSync` 不参与，直接用 `ColorFiltered`），磨皮/锐化/颗粒等细节效果只作用于成片。

为什么 Android 不跟？因为我们曾经真试过在 Dart 层做"逐帧美颜"：Ticker 驱动 `RepaintBoundary.toImage()` 读回像素，再叠加半透明处理层。实测在 OHOS 上单帧读回就要数百毫秒（快门冻结帧实测 455ms@1.0x），取景器直接变幻灯片；而且预览分辨率下的轻量磨皮核视觉上几乎不可感知。这条路被证伪后，我们回退成"能力差异下的务实选择"：**预览求流畅，成片求效果**。

同类取舍还有"拉腿预览"：早期同样是"抓帧 → isolate 逐像素拉伸 → 半透明幽灵叠加"，结果既有 GPU 读回卡顿又有新旧帧重影。最终换成**双层 GPU 合成**——纹理层直接以两个 `Texture` 渲染（锚点上方恒等、下方纵向放大），零读回、零 CPU 拉伸、零半透明叠层，且与成片的拉伸几何一致。

## 六、小结

"在取景器上盖一张图"这句话，拆开是四个工程问题：**坐标系要跟比例走（存百分比）、交互层要透传（IgnorePointer + 手势竞技场）、资源要按源分流（三类三条路径）、端侧能力要认（能原生就原生，不能就明确降级）**。

# 【第三波 · 2026-10-05】Flutter 一键生成带二维码的分享海报：海报合成 + 分享闭环的实现思路

> 第三波定位：**技术长文 · 功能闭环**。整篇只钻一个功能——「拍完 → 合成带二维码的海报 → 保存/分享 → 对方扫码拍同款」这条链路在 Flutter 侧怎么落地。文中实现均来自仓库真实代码（`lib/shared/services/poster_generator.dart`、`lib/features/templates/services/template_share_code.dart`、`lib/core/utils/safe_share.dart`），面向 Flutter / 鸿蒙开发者。

## 一、把"分享"做成一个闭环

普通分享是把图片甩出去，链路到这就断了。我们想做的多一点：**海报上带一个二维码，对方扫码就能拿到你这张照片用的模板**，形成"我拍 → 你扫 → 你拍同款"的闭环。

拆开看，这个功能有四个环节，每个都有坑：

1. **合成**：把照片、水印、文案、二维码拼成一张固定尺寸的海报，并捕获成 PNG；
2. **渲染**：海报有多种版式可切换，预览要跟手、导出要清晰；
3. **编码**：二维码里放什么，才能扫得动又扫得准；
4. **落地**：保存到相册、调起系统分享，还要在鸿蒙上跑通。

下面按这四步讲。

## 二、合成：RepaintBoundary.toImage 与"1080 宽"导出口径

Flutter 里把一棵 Widget 树截成图片，标准做法是 `RepaintBoundary` + `RenderRepaintBoundary.toImage`。我们把它收敛进一个通用生成器 `PosterGenerator`，调用方只传内容 Widget 和一个 `GlobalKey`：

```dart
final boundary = key.currentContext?.findRenderObject() as RenderRepaintBoundary?;
if (boundary == null || boundary.size.isEmpty) return null;
final pixelRatio = (kPosterExportWidth / boundary.size.width).clamp(2.0, 4.0);
return boundary.toImage(pixelRatio: pixelRatio);
```

这里有两个刻意的决定：

**其一，导出倍率按"目标宽度"反算，而不是固定 3x。** 我们支持全屏 9:16、3:4、1:1、4:3、16:9 五种比例（`PosterRatio` 由图片宽高比归类）。如果无脑固定 `pixelRatio: 3`，9:16 竖图按设计逻辑宽算出来只有 900px 宽，清晰度不够。改成"统一以 ≥1080px 物理宽出图"：

```dart
static const double kPosterExportWidth = 1080;
final ratio = (kPosterExportWidth / size.width).clamp(2.0, 4.0);
```

`clamp(2.0, 4.0)` 是防呆：小画布别算出离谱的大倍率，大画布也别低于 2x。

**其二，捕获的是"内容本体"，不是预览容器。** 预览区通常套了 `FittedBox` / `Center` / 背景色，如果连容器一起截，导出图会带上容器的背景填充和边距。所以我们让每个版式各自持有一个 `GlobalKey`，`toImage` 只盯海报本体——这样预览缩放（视觉）和导出分辨率（像素）彻底解耦。

## 三、离屏预渲染：为什么要把海报画到屏幕外

海报有多个版式，横向 PageView 切换。如果每个版式都用 live Widget 渲染，在鸿蒙设备上左右滑动会明显掉帧——一页海报里可能有封面解码、渐变、阴影、二维码，同时渲染两页开销不小。

解法是把每个版式**离屏预渲染成位图**，PageView 里改成平移 `RawImage`：

```dart
// 挂到屏幕外渲染，避免渲染瞬间闪现
final entry = OverlayEntry(
  builder: (ctx) => Positioned(
    left: 30000,
    top: 0,
    child: RepaintBoundary(
      key: renderKey,
      child: Material(type: MaterialType.transparency, child: poster),
    ),
  ),
);
overlay.insert(entry);
try {
  final boundary = await _settleBoundary(renderKey);
  return boundary?.toImage(pixelRatio: pixelRatio);
} finally {
  entry.remove(); // 捕获完立刻移除
}
```

几个细节值得说：

- **用 `OverlayEntry` + `Positioned(left: 30000)` 挂到屏幕外**，比 `Offstage` 好：`Offstage` 不参与布局（拿不到尺寸），而我们要的是"正常布局、只是看不见"。
- **外面包一层 `Material(type: MaterialType.transparency)`**。离屏的 Overlay 没有 `Material` / `Scaffold` 祖先，海报里的 `Text` 拿不到 `DefaultTextStyle`，某些引擎上会渲染出黄色双下划线。包一层透明 `Material` 提供默认文本样式，不影响透明背景和捕获结果。
- **捕获后立即 `entry.remove()`**，别把离屏树一直挂在树上。

还有个容易踩的坑：**PageView 相邻两页会同时挂在渲染树上，如果共用同一个 `GlobalKey`，会触发 `Duplicate GlobalKey`，Flutter 直接截断整棵子树。** 所以每个版式页用独立的 key：

```dart
final Map<int, GlobalKey> _styleContentKeys = {};
// ...
RepaintBoundary(
  key: _styleContentKeys.putIfAbsent(i, () => GlobalKey()),
  child: style.builder(_data),
)
```

## 四、等图片解码：一个"遍历渲染树"的土办法

`toImage` 有个隐性前提：**这棵子树里的图片必须已经解码完成**，否则截出来是空白或占位图。海报里有照片封面、二维码，都可能异步解码。

Flutter 没有直接给出"这棵树里的图片是否都 ready"的公开 API，我们的做法是遍历渲染树，找还在加载的 `RenderImage`：

```dart
bool _treeImagesReady(RenderObject root) {
  var pending = false;
  void visit(RenderObject node) {
    if (!pending && node is RenderImage && node.image == null) pending = true;
    if (!pending) node.visitChildren(visit);
  }
  visit(root);
  return !pending;
}
```

再配合"每 16ms 一帧、超时 2500ms"的轮询：

```dart
while (sw.elapsed < timeout) {
  await Future<void>.delayed(const Duration(milliseconds: 16));
  await WidgetsBinding.instance.endOfFrame;
  final b = key.currentContext?.findRenderObject() as RenderRepaintBoundary?;
  if (b == null || !b.attached) return null;
  if (_treeImagesReady(b)) return b;
}
```

`endOfFrame` 保证等到本帧画完再判断，避免刚挂上就下结论。超时后兜底返回上一次拿到的 boundary——宁可清晰度打折，也别让用户卡在"生成中"。

## 五、二维码：内容越长，越扫不动

海报里的二维码尺寸只有几十到一百多 px（各版式不同），这决定了**二维码内容不能长**。

我们二维码放的是一个自定义 scheme 的分享链接：

```
lumira://tpl/{base64url(json)}
```

关键在 `json` 用哪个版本。模板导出有两种：

| 格式 | 内容 | 体积 | 模块数 |
|---|---|---|---|
| `.pptpl` | 完整 6 区段，内嵌 base64 封面 / 剪影 | 约 2261 字节 | 约 157 模块 |
| `.lumira` | 简化版，仅基础信息 | 约 445 字节 | 约 73 模块 |

如果海报二维码用完整 `.pptpl`，2261 字节会生成约 157 模块的高密度码；缩到海报的小尺寸后，直接糊成一团黑点，扫不动。所以**海报一律用简化链接**：

```dart
/// 构建海报二维码内容：统一使用低密度简化 .lumira 链接。
static String buildPosterQrData(TemplateRecord record) =>
    buildShareLink(record, usePptpl: false);
```

渲染用 `qr_flutter`：

```dart
QrImageView(
  data: buildTemplatePosterQrData(template),
  version: QrVersions.auto, // 让库按数据量自选版本
  size: 140,
  eyeStyle: QrEyeStyle(eyeShape: QrEyeShape.square, color: tokens.textPrimary),
  dataModuleStyle: QrDataModuleStyle(
    dataModuleShape: QrDataModuleShape.square,
    color: tokens.textPrimary,
  ),
)
```

解析侧要把 `lumira://tpl/{base64}` 和 `https://lumira.app/tpl/...` 两种形式都吃下（`TemplateShareCode.parseLink`），并保持生成 / 解析往返一致——这条有单测盯着。

## 六、保存与分享：三平台降级链

**保存到相册**：

- iOS / Android：走 `saver_gallery` 的 `SaverGallery.saveImage`；
- HarmonyOS：`saver_gallery` 没有 ohos 实现，会抛 `MissingPluginException`。我们捕获后降级到自建原生通道：

```dart
const channel = MethodChannel('lumira/photo_saver');
final result = await channel.invokeMethod('saveToAlbum', {'path': file.path});
```

**调起分享**：统一走一层 `SafeShare` 包装器。它的降级顺序是：

1. iOS / ohos：先试原生通道 `MethodChannel('lumira/system_share')` 的 `shareFiles`；
2. 失败或非上述平台：退回 `share_plus` 的 `Share.shareXFiles`；
3. 再抛 `MissingPluginException`：降级到"把文件路径复制到剪贴板"并 toast 提示。

```dart
try {
  await Share.shareXFiles(files, subject: subject, text: text);
} on MissingPluginException {
  await _fallbackToClipboard(files.first.path);
}
```

之所以先走原生通道，是因为鸿蒙上 pub.dev 版 `share_plus` 缺原生实现；先试原生成功率高，失败再逐级回退，用户感知只是"分享面板换了形式"，不会白屏或报错。

## 七、踩坑清单

- 离屏 Overlay 无 `DefaultTextStyle` → 文字出现黄色双下划线：包透明 `Material`；
- PageView 相邻页共用 `GlobalKey` → `Duplicate GlobalKey` 截断子树：**按页独立 key**；
- `toImage` 前图片没解码完 → 截出空白：先遍历 `RenderImage` 确认 ready；
- 导出固定 3x → 9:16 竖图偏糊：改按"1080 宽"反算倍率；
- 捕获预览容器 → 导出图带背景和边距：改"内容级捕获"；
- 鸿蒙 `saver_gallery` / `share_plus` 无原生实现 → `MissingPluginException`：分别降级到自建通道 / 剪贴板；
- 二维码内容过长 → 小尺寸糊成一团：海报只用简化链接。

## 八、小结

"一键生成分享海报"这句话，拆开是四件事：**合成要定死导出口径（1080 宽 + 内容级捕获）、渲染要离屏预渲染成位图、二维码要控长度、落地要给鸿蒙留降级链**。把二维码放进海报，分享就不再是终点，而是下一张照片的起点。
