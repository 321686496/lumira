# 一款相机类 Flutter 应用上架鸿蒙 NEXT，我们踩过的坑都在这了

> 本文来自「如画 Lumira」开发团队。这是一款把摄影师摆姿经验做成"取景框内叠加姿势剪影"的摄影辅助 App，刚以同一套 Dart 代码库，同时上架了 iOS App Store 与华为应用市场（鸿蒙 HarmonyOS 版）。相机是端侧依赖最重的一类应用——取景器、预览流、相册、权限、本地存储一个都不能少，所以这次适配踩的坑对大多数普通 App 也有参考价值。全文以真实工程记录为准，不含广告成分。

## 一、先说结论（给赶时间的同学）

1. **Flutter 官方至今不官方支持鸿蒙**，社区/华为维护的 Flutter OHOS fork 是目前唯一现实路径，代价是锁死在较低版本（我们锁定 Flutter 3.7.12 / Dart 2.19.6）。
2. 版本锁死的连锁反应比想象中大：不是"把依赖升上去"而是"把依赖全部降下来"，几乎每个主流插件都要处理一遍版本兼容。
3. 插件生态分三类处理：**有社区 OHOS 适配版 → 直接换源；没有适配版 → 包一层运行时分发；核心插件（相机）有 bug → 自建 vendor fork 补丁**。
4. 最深的坑都在相机链路：OHOS 端取景器初始化、iOS 端预览与成片视场一致性（这是原版插件 bug，两端都躲不掉）。
5. 值不值得上鸿蒙？**如果目标是"早期生态曝光红利"，值得；如果预期"适配成本可控"，不现实。**（细节见文末）

## 二、背景：为什么相机类应用上鸿蒙格外难

HarmonyOS NEXT（纯血鸿蒙）不再兼容安卓 AOSP，意味着所有依赖 Android 实现的插件在鸿蒙上都是"零基础"状态——不是"跑得慢"，是**根本没有实现**。

我们的 App「如画 Lumira」核心体验是：用户选一个姿势模板，取景框上实时叠加人形剪影，照着摆就能拍。所以引擎对系统的依赖清单是相机类 App 的"全家桶"：

- 相机取景器 + 拍照（核心路径）
- 实时预览叠图渲染
- 权限（相机 / 麦克风 / 相册）
- 本地数据库（离线优先的模板与照片索引）
- 文件选择（模板导入）

其中任何一环缺 OHOS 实现，整条链路就是断的。这也是我们评估时最犹豫的点：**跨平台框架解决的是 UI 与业务逻辑，而相机类应用的灵魂恰恰在原生层。**

## 三、版本锁死：一切问题的起点

Flutter 的鸿蒙适配由华为与社区（CPF-Flutter 等）在 fork 上推进，我们接入时的稳定组合是：

```
Flutter 3.7.12 / Dart 2.19.6
```

这个版本号意味着什么？**Dart 3 之前的最后一个大版本区间**。于是所有在 Dart 3 时代"理所当然"的依赖，全部要降级，而且降级链条环环相扣。举一个我们记录在案的例子：

> `flutter_riverpod` 一旦解析到 2.4.10，会硬依赖 `riverpod 2.5.0`，而 2.5.0 使用了 `@mustBeOverridden` 注解，需要 `meta 1.12.0+`；但鸿蒙版 Flutter 3.7 必须使用 `meta 1.8.0`。于是最终钉死 `flutter_riverpod 2.3.6`。

同理：`go_router` 只能用 6.x（14.x 需 Dart 3），`permission_handler` 只能用 10.3.2（11+ 需 Dart 3）。

**经验一：在鸿蒙 fork 上开工前，先建一张"依赖版本兼容表"，从 pubspec.lock 反向约束，而不是让 pub 解析器自由发挥。** 解析器不知道你在鸿蒙上，它会给你一个"逻辑正确、原生缺失"的依赖树——编译可能都没问题，运行时才炸。

另一个实战建议：**关键 fork 从 git 依赖本地化为 path 依赖**。我们把相机插件的 fork 拉到本地仓库维护（`path:` 引用），一是方便打补丁，二是避免上游 force-push 后 `pub cache` 指向脏提交（`flutter pub clear` 清不掉的坑）。

## 四、插件生态的三类处理姿势

把我们的依赖按处理方式分三类，基本覆盖了常见插件的全部处境：

### 1. 有社区 OHOS 适配版 → 换源 + 版本对齐

| 插件 | 处理 |
|---|---|
| 相机 camerawesome | 换用 gitcode fork 的 `camerawesome_ohos 1.0.2`（对应原版 1.4.0） |
| 权限 permission_handler | 换 CPF-Flutter 适配版 10.3.2 |
| 文件选择 file_picker | 同一 fork 的 `ohos` 子目录包 `file_picker_ohos` |
| 数据库 sqflite | 换 CPF-Flutter 鸿蒙适配版 2.2.8+4 |

注意适配版与原版的**包名往往不同**（`camerawesome_ohos` vs `camerawesome`）。我们的做法是业务代码只 import 自己的接口层，由底层的包装器按平台做运行时分发——以文件选择为例，iOS/Android 走原版 `file_picker`，OHOS 走 `file_picker_ohos`，两者 API 完全一致，通过一个 `FilePickerService` 包装器分发。**业务层永远不知道自己跑在哪个平台上**，这条纪律为后面换插件、改 fork 省了大量重构。

### 2. 没有适配版 → FFI 不一定是出路

sqflite 我们最初试过 FFI 方案（绕开 platform channel 直接加载原生 so），**失败原因很有代表性：OHOS 的 so 重定位类型与预期不兼容**，这条路直接废弃，最终回到社区维护的鸿蒙适配版。

**经验二：评估"某个插件鸿蒙上怎么跑"时，先查 CPF-Flutter 的适配库清单，再考虑 FFI/自研。** 适配库覆盖不到、又属于核心路径的，才有必要投入自研，并且要提前验证 so 的加载与重定位约束。

### 3. 有适配版但有 bug → 自建 vendor fork

这是我们投入最深的一块，也是对 iOS 用户感知最直接的一块：

> 原版 camerawesome 1.4.0 的预览 cover 计算有 bug：**竖屏下纹理永远按高度适配**，导致预览画面与实际成片不一致（所见非所得）；同时 iOS 预览流选择 16:9 视频 preset，而实际成片是 4:3——预览视场与成片视场不一致，用户按快门前看到的构图，和拍下来的不一样。

对普通 App 这是"显示小问题"，对拍照 App 这是**致命伤**：我们的产品价值就建立在"取景框里的剪影 = 最终照片的构图"上，预览和成片差一点，产品就不成立。

我们的处理：在本地 `packages/camerawesome` 维护了一个与原版同版本号、只打 iOS/预览适配补丁的 vendor 包，修正 cover 算法与 preset 选择，保证"所见即所得"。

**经验三：相机类应用的第一验收标准是 WYSIWYG（所见即所得），把它写进自动化测试与 CI 截图比对，而不是靠人眼抽检。** 顺带一提，`camerawesome_ohos` 最初在鸿蒙端也出现过取景器一直转圈的初始化问题，最后定位到适配版的实现并换到可用的 fork 版本才解决——相机插件的"能编译"与"能出图"之间，隔着一条鸿沟（物理意义上的）。

## 五、UI 体系与业务层：迁移成本比预期低的部分

好消息是：一旦插件层跑通，**Dart 层的业务代码几乎零改动**。我们的 UI 是自建的四套风格（新拟态/扁平/玻璃/女性美学）× 八款主题色的设计 token 体系，全部派生自统一的 `AppThemeData`，没有使用平台原生控件，所以在鸿蒙上天然"所见即所得"。离线优先架构（sqflite 本地库 + 服务端只读同步）也让鸿蒙端可以独立运行，不强依赖后端。

真正要额外处理的集中在：

- 启动链路：初始化失败的兜底（避免白屏无反馈），鸿蒙端对首帧的时序与 iOS 有差异；
- 平台通道相关：扫码识别限幅、原生侧白平衡扩展这类原生能力，需要分别在鸿蒙侧补实现；
- 发布链路：鸿蒙的签名体系（p7b）与 iOS 完全是两套，CI 上要分别维护。

## 六、CI 建议

我们的 CI 用 GitHub Actions 验证 `flutter analyze + test`（锁定 Flutter 3.7.12），iOS 打包也在 Actions 上完成。给同样双端团队的建议：

1. **分析器锁版本**：Dart 2.19 与 3.x 的 lint 行为差异不小，CI 的 Flutter 版本必须与鸿蒙 fork 对齐，否则"本地过了 CI 挂"；
2. **path 依赖进仓库**：所有 fork 一律以 path 依赖入库，CI 不依赖外部 git 状态；
3. **双端 UI 截图基线**：至少覆盖相机取景器叠图这一核心场景，防回归。

## 七、所以，现在该不该上鸿蒙？

我们的判断标准是三个问题：

1. **你的目标用户里有没有华为存量用户？** 有的话，NEXT 上没有微信支付宝之外太多替代品，早到 = 竞争少。
2. **你的 App 重不重原生？** 轻原生（列表/表单/内容型）适配成本可控；重原生（相机/音视频/地图）请按 1.5-2 倍预估工作量，并且给相机链路留足"预览正确性"的专项验证时间。
3. **团队能不能接受版本锁死？** Dart 2.19 意味着放弃 3.x 生态（records、pattern matching、新插件），这对新项目是长期税。

对我们来说，三个答案都是"是/重/能"，所以做了。如果你在做工具类、相机类的 Flutter 应用，正在评估鸿蒙，欢迎评论区交流，我们把没写进文章的细节都攒着。
